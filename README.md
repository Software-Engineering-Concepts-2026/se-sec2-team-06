## ── 2. กฎการสื่อสารและการตอบกลับ (Communication Rules) 💬 ──
เพื่อความสุขในการทำงานและการเรียนร่วมกันอย่างลงตัว:

*   **📢 เน้นคุยห้องสาธารณะ:** พูดคุยเรื่องงาน เทคนิค หรือการออกแบบในช่องสาธารณะ (เช่น `#dev`, `#design`) เป็นหลัก หลีกเลี่ยงการทักแชตส่วนตัว (DM) เพื่อให้ทุกคนเห็นข้อมูลตรงกัน
*   **🧵 ใช้ระบบตั้งเป้าตอบกลับ (Thread):** พิมพ์ตอบโต้ในกระชับกลุ่มข้อความเก่า (Thread) เสมอ เพื่อไม่ให้หน้าแชตรวมสับสนและจับประเด็นยาก
*   **⏰ เวลาตอบกลับที่คาดหวัง:**
    *   *เวลาปกติ (09:00 น. - 21:00 น.):* ตอบกลับภายใน **4 ชั่วโมง**
    *   *ช่วงดึก / วันหยุด:* ตอบกลับภายใน **12 ชั่วโมง** (หรือช่วงเช้าของวันถัดไป)
    *   *หมายเหตุ:* หากติดเรียน/เตรียมสอบ ให้ตั้งข้อความสถานะในแอปพลิเคชันว่า **"Busy/Away"** ไว้ล่วงหน้า
*   **🚨 กรณีด่วนที่สุด:** หากบิลด์ระบบพัง โค้ดรันไม่ได้ หรือเซิร์ฟเวอร์ล่ม ให้แท็กคนรับผิดชอบตรง ๆ `@username` (ใช้แท็กกลุ่ม `@here` เฉพาะเมื่อจำเป็นเท่านั้น)

## ── 3. ขั้นตอนการจัดการซอร์สโค้ด (Git & Review Workflow) 💻 ──
เราใช้กระบวนการ **Git Feature Branch Workflow** เพื่อป้องกันระบบพัง

### 🌿 กฎการสร้างกิ่งโค้ด (Branching Stratergy)
*   `main` ➔ **สำหรับขึ้นระบบจริงเท่านั้น** ต้องเป็นโค้ดที่รันได้ 100% *ห้ามแก้ไขโค้ดที่กิ่งนี้โดยตรงเด็ดขาด*
*   `develop` ➔ **กิ่งรวมศูนย์** โค้ดของทุกฟีเจอร์ที่พร้อมทดสอบแล้วจะมารวมกันที่กิ่งนี้
*   `feature/[ชื่อฟีเจอร์สั้นๆ]` ➔ **กิ่งทำงานเฉพาะตัว** ถูกแตกมาจาก `develop` (เช่น `feature/user-login`)

### 📝 มาตรฐานการเขียนชื่อ Commit (Commit Messages)
เราเขียนสั้น ๆ เป็นภาษาอังกฤษตามมาตรฐาน **Conventional Commits**: `<ประเภท>: <รายละเอียด>`
*   `feat: add login validation` (เมื่อสร้างฟีเจอร์ใหม่)
*   `fix: resolve crash on null pointer` (เมื่อแก้ไขจุดบกพร่อง)
*   `docs: update setup guide in README` (เมื่อแก้ไขเอกสารคู่มือ)

### 🔍 กระบวนการตรวจการบ้านและรวมโค้ด (Pull Request & Review)
1.  **เปิด PR:** เมื่อเขียนฟีเจอร์เสร็จเรียบร้อย ให้ส่งคำขอ Pull Request (PR) จากกิ่งทำงานตัวเองกลับเข้าสู่กิ่ง `develop`
2.  **ระบุคนช่วยตรวจ:** แท็กชื่อเพื่อนในทีมอย่างน้อย **1 คน** ให้มาเป็นผู้ตรวจโค้ด (Reviewer)
3.  **เงื่อนไขในการกดเคลียร์เข้ากิ่งหลัก:**
    *   ✅ บิลด์ผ่าน (ไม่ติด Error ในระบบของทีม)
    *   ✅ ได้รับการกด **Approve** จากเพื่อนร่วมทีมที่สุ่มไปตรวจอย่างน้อย **1 คน**
    *   ✅ ถกถามคำถามต่าง ๆ ในช่องคอมเมนต์ของ PR จนได้ข้อสรุปจนหมดแล้ว
4.  **ห้ามอนุมัติงานตัวเอง:** ผู้เป็นเจ้าของโค้ดไม่มีสิทธิ์กด Approve หรือกดรวมโค้ด (Merge) งานของตนเองเข้ากิ่งกลาง
