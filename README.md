
## ── 3. ขั้นตอนการจัดการซอร์สโค้ด (Git & Review Workflow) 💻 ──

### 🌿 Branching Strategy

* **`main`** ➔ สำหรับโค้ดที่ผ่านการทดสอบและพร้อมส่งมอบ

  * ต้องเป็นโค้ดที่มีความเสถียรและพร้อมใช้งาน
  * 🚫 ห้ามแก้ไขหรือ Commit ลงบนกิ่งนี้โดยตรง
  * ✅ อนุญาตให้ Merge เฉพาะโค้ดที่ผ่านการ Review และการทดสอบเรียบร้อยแล้ว

* **`develop`** ➔ กิ่งหลักสำหรับการพัฒนา (Integration Branch)

  * ใช้สำหรับรวมโค้ดจากทุกฟีเจอร์ที่พัฒนาเสร็จและพร้อมทดสอบร่วมกัน
  * ทุก Feature Branch จะถูกสร้างจากกิ่งนี้ และ Merge กลับเข้ามาที่กิ่งนี้เมื่อพัฒนาเสร็จ

* **`feature/<feature-name>`** ➔ กิ่งสำหรับพัฒนาฟังก์ชันเฉพาะ

  * สร้างขึ้นจาก `develop`
  * ใช้สำหรับพัฒนา ทดสอบ และแก้ไขฟีเจอร์โดยไม่กระทบต่อการทำงานของทีม
  * ตัวอย่าง: `feature/user-login`

### 📝 มาตรฐานการเขียน Commit Message

ใช้รูปแบบ **Conventional Commits**

`<type>: <description>`

ตัวอย่าง:

* `feat: add login validation`
* `fix: resolve crash on null pointer`
* `docs: update setup guide in README`

### 🔍 Pull Request & Code Review Process

1. **สร้าง Pull Request (PR)**

   * เมื่อพัฒนาฟีเจอร์เสร็จเรียบร้อย ให้เปิด Pull Request จาก Feature Branch ไปยัง `develop`

2. **กำหนด Reviewer**

   * ระบุผู้ตรวจสอบโค้ด (Reviewer) อย่างน้อย **1 คน**

3. **เงื่อนไขก่อนการ Merge**

   * ✅ Build และ Automated Checks ผ่านทั้งหมด
   * ✅ ได้รับการ Approve จาก Reviewer อย่างน้อย **1 คน**
   * ✅ ข้อคิดเห็นและคำถามใน Pull Request ได้รับการตอบและสรุปครบถ้วน
   * ✅ ไม่มี Conflict กับกิ่งเป้าหมาย

4. **การอนุมัติและ Merge**

   * 🚫 ผู้พัฒนาไม่สามารถ Approve งานของตนเองได้
   * 🚫 ไม่ควร Merge Pull Request ของตนเองก่อนได้รับ Approval จาก Reviewer
   * ✅ ควรมีการตรวจสอบโค้ดโดยสมาชิกทีมอย่างน้อย 1 คนก่อน Merge

> **Code Review Policy:** ทุก Pull Request ต้องผ่านการตรวจสอบ (Code Review) และได้รับ Approval ก่อน Merge เพื่อรักษาคุณภาพ ความถูกต้อง และมาตรฐานของซอร์สโค้ดภายในทีม

## ── 4. แนวทางการตัดสินใจของทีม 🤝 ──

ทีมให้ความสำคัญกับการสื่อสารและการแลกเปลี่ยนความคิดเห็นอย่างเปิดกว้าง โดยจะพยายามหาข้อสรุปร่วมกันผ่านการพูดคุยและรับฟังมุมมองของสมาชิกทุกคน

### 💬 การตัดสินใจทั่วไป

* งานหรือประเด็นที่มีผลกระทบในวงจำกัด สามารถให้ผู้รับผิดชอบงานเป็นผู้ตัดสินใจได้
* สมาชิกในทีมสามารถเสนอความคิดเห็นหรือข้อกังวลเพิ่มเติมได้ก่อนสรุปผล
* ผู้รับผิดชอบควรพิจารณาข้อเสนอแนะของทีมก่อนดำเนินการ

### 🧩 กรณีมีหลายแนวทางให้เลือก

เมื่อเกิดความเห็นที่แตกต่างกันเกี่ยวกับการพัฒนา การออกแบบ หรือการแก้ปัญหา ทีมจะดำเนินการตามลำดับดังนี้

1. ระบุทางเลือกที่เป็นไปได้ให้ชัดเจน
2. วิเคราะห์ข้อดี ข้อเสีย และผลกระทบของแต่ละทางเลือก
3. เปิดโอกาสให้สมาชิกทุกคนแสดงความคิดเห็น
4. ร่วมกันหาข้อสรุปที่เหมาะสมที่สุดสำหรับโครงการ

### 📌 การตัดสินใจที่สำคัญ

สำหรับการตัดสินใจที่ส่งผลต่อโครงสร้างหลักของระบบ ขอบเขตโครงการ หรือประสบการณ์การใช้งานของผู้ใช้

* ควรบันทึกเหตุผลและแนวคิดที่ใช้ประกอบการตัดสินใจ
* เพื่อใช้เป็นข้อมูลอ้างอิงในกรณีที่ต้องกลับมาทบทวนในอนาคต

### 🚀 การดำเนินงานหลังการตัดสินใจ

เมื่อทีมได้ข้อสรุปร่วมกันแล้ว สมาชิกทุกคนจะร่วมกันดำเนินงานตามแนวทางที่ตกลงไว้ และช่วยกันผลักดันให้บรรลุเป้าหมายของโครงการ
