## Reflection on Software Craftsmanship

### 1. Software Entropy และ Broken Window Theory

ในโปรเจกต์พัฒนาแอปพลิเคชันมือถือที่เคยทำ "หน้าต่างที่แตก" ที่ข้าพเจ้าเคยปล่อยปละละเลยคือการปล่อย Warning และ TODO หลายจุดไว้ในโค้ดโดยคิดว่าจะกลับมาแก้ไขในภายหลัง เนื่องจากโปรแกรมยังสามารถทำงานได้ตามปกติ

อย่างไรก็ตาม เมื่อเวลาผ่านไป Warning และ TODO เหล่านั้นไม่ได้รับการแก้ไข กลายเป็นตัวอย่างที่ทำให้สมาชิกในทีมเริ่มละเลยมาตรฐานการเขียนโค้ดเช่นเดียวกัน มีการเพิ่มโค้ดที่ยังไม่สมบูรณ์เข้าไปมากขึ้นเรื่อย ๆ ส่งผลให้โครงสร้างของโปรแกรมซับซ้อนขึ้น เกิดความสับสนในการบำรุงรักษา และใช้เวลามากขึ้นในการแก้ไขข้อผิดพลาด

เหตุการณ์นี้สะท้อนแนวคิด Broken Window Theory ที่กล่าวว่า หากมี "หน้าต่างที่แตก" เพียงบานเดียวและไม่มีใครซ่อมแซม คนอื่นก็มีแนวโน้มที่จะละเลยมาตรฐานและสร้าง "หน้าต่างที่แตก" เพิ่มขึ้นอีก ในงานพัฒนาซอฟต์แวร์ ผลลัพธ์คือการเกิด Software Entropy หรือความเสื่อมถอยของคุณภาพระบบเมื่อเวลาผ่านไป ดังนั้นจึงควรแก้ไขปัญหาเล็ก ๆ ตั้งแต่พบเห็น เพื่อรักษาคุณภาพของระบบในระยะยาว

### 2. Take Responsibility และ Provide Options, Don't Make Lame Excuses

ในความเข้าใจของข้าพเจ้า หลักการ "Take Responsibility" คือการรับผิดชอบต่อหน้าที่และผลลัพธ์ของงานที่ได้รับมอบหมาย เมื่อเกิดปัญหาควรมุ่งเน้นการแก้ไขปัญหามากกว่าการหาข้ออ้าง

สำหรับโปรเจกต์นี้ หากข้าพเจ้าพบว่าฟีเจอร์ที่รับผิดชอบมีความซับซ้อนกว่าที่ประเมินไว้และอาจไม่เสร็จตามกำหนด ข้าพเจ้าจะไม่บอกเพียงว่า "ทำไม่ทัน" หรือ "งานยากเกินไป" แต่จะเสนอทางเลือกให้ทีมพิจารณา เช่น

* ส่งมอบเวอร์ชันพื้นฐานของฟีเจอร์ก่อน
* ขอความช่วยเหลือจากสมาชิกที่มีความเชี่ยวชาญในส่วนที่ติดปัญหา
* ปรับลำดับความสำคัญของงานเพื่อให้ส่วนสำคัญเสร็จก่อน
* ขอขยายเวลาโดยระบุเหตุผลและกำหนดส่งใหม่อย่างชัดเจน

แนวทางนี้สอดคล้องกับหลักการ "Provide Options, Don't Make Lame Excuses" เพราะเป็นการนำเสนอทางออกที่ช่วยให้ทีมตัดสินใจได้ แทนการให้ข้อแก้ตัวที่ไม่ก่อให้เกิดประโยชน์ต่อโครงการ
