# Persistent Profile Images and Document Files

## Status

Draft for user review. The user approved this workstream and its order; this document makes its implementation behavior explicit. No application code, cloud project, or deployment has been changed.

## Goal

Keep learner profile pictures and document-library uploads available both in local development and after a Render restart/redeploy, while keeping each learner's files private and preserving the current same-origin API.

## Approved decisions

- Use Supabase Storage for deployed profile-image and document bytes. Use two private buckets: `profile-avatars` and `documents`.
- Keep the existing local filesystem storage as the default when Supabase Storage is not configured, so the current local workflow remains simple.
- Store only opaque object keys and file metadata in the application database; never store file bytes in Postgres or expose a Supabase secret/public object URL to the browser.
- Keep current file rules: profile images are validated JPEG/PNG/WebP up to 5 MB; documents remain PDF/DOCX/MD/TXT up to 20 MB.
- Preserve existing authentication and API routes. A request must resolve the owning user/document from the database before a server-side Storage read, update, or delete.
- Configure Storage with a server-only secret. The browser continues to call the app's authenticated API; private objects are not directly public or shared.
- Do not automatically copy files already present in a developer's local folder to Supabase. Explain that existing files remain local until re-uploaded or migrated with a separate deliberate tool.
- Add configuration and setup guidance for local and Render environments, but do not create a cloud project, set production values, or deploy as part of this implementation.

## User experience

- An uploaded avatar remains visible after a page reload and is served through the current authenticated profile API.
- An uploaded document remains listed and can still be opened/downloaded after an API restart or Render redeploy.
- Upload validation, progress/errors, rename/tag behavior, and per-document delete confirmation keep their current user-facing behavior.
- A failed Storage write must not leave a visible database record pointing to a missing object. A failed metadata commit must remove the newly uploaded object when possible.
- If a previously stored object cannot be read, return a clear unavailable-file response rather than a broken or public URL.

## Storage and ownership model

- Add a small storage-provider boundary used by profile and document services. It supports save/read/delete (and document staging/finalization or an equivalent transactional cleanup strategy) without leaking provider details into route handlers.
- Supabase object keys are generated by the server and scoped by owner, for example `{user_id}/{opaque_random_key}`. Original filenames are metadata only and never become object paths.
- Keep database ownership as the source of authorization. For document requests, load the document under `document_id + current_user.id` before touching Storage. For avatars, resolve the current account's `avatar_key` before reading/deleting.
- Use the service-role/secret credential only in the FastAPI process. It bypasses Storage RLS, so route-level owner checks and opaque, unguessable keys are mandatory. Never return the secret, key, bucket management credentials, or a permanent public URL to the client.
- Configure private buckets with limits and allowed content types matching the existing upload validators. Do not rely on bucket MIME restrictions as a replacement for application validation.
- Existing local adapter remains usable with tests and local `.env`; production configuration selects the Supabase adapter explicitly. Partial cloud configuration fails with an actionable startup/configuration error instead of silently falling back to ephemeral Render disk.
- Any delete/replace flow must account for DB and object-store operations not sharing a transaction. Use compensating cleanup and preserve the existing old avatar/document until the replacement metadata is committed; failed cleanup is logged and retriable, not reported as a successful data deletion.

## Configuration and operations

- Add empty names (not values/secrets) to the environment example: `SUPABASE_URL`, `SUPABASE_SECRET_KEY`, and optional bucket-name overrides only if the implementation needs them. `SUPABASE_PUBLISHABLE_KEY` and `SUPABASE_JWKS_URL` are not needed for this server-side Storage-only integration unless existing app auth code independently requires them.
- Add instructions for creating the two private buckets and setting Render variables. Keep the secret out of Vite/client variables, committed files, logs, and error messages.
- Local mode requires no cloud credentials. Cloud mode requires both URL and secret key and uses the same private-bucket configuration.
- Document that current Render filesystem uploads are ephemeral and that switching to cloud storage will not discover or preserve old ephemeral files.

## Acceptance criteria

1. With no Supabase configuration, the current local upload/read/delete flows work through the local adapter.
2. With a fake Supabase Storage transport, avatar and document bytes can be saved, read, and deleted from private object keys; keys are generated safely and do not include untrusted filenames.
3. Uploading a profile picture updates only the signed-in user's avatar; a second user cannot retrieve or delete it.
4. Uploading a document persists the original file and its metadata; only its owner can retrieve, download, or delete it.
5. Replacing/deleting a document or avatar does not affect another object or another user's record; failure paths do not leave a misleading visible record.
6. Existing file type, size, content-signature, and authentication protections remain enforced for both providers.
7. Cloud configuration is all-or-nothing and reports missing configuration clearly; the secret never appears in client responses or logs.
8. The Render setup guide identifies where to add server environment variables and how to create private buckets without including any live credentials.
9. Existing local files are not silently copied, deleted, or claimed to be migrated.

## Out of scope

- Deploying to Render, changing Supabase production settings, provisioning cloud infrastructure, or handling credentials on behalf of the user.
- Public or cross-user file sharing, signed URLs, CDN access, direct browser uploads, tutor-chat attachment persistence, and automatic migration of existing local/ephemeral files.
- Moving application relational data from SQLite to Postgres; this work changes only file-byte storage.

## Notes

This spec supersedes the local-only file-storage choice in `2026-10-11-document-library-and-reader-design.md` for profile images and document-library file bytes. The local adapter remains supported. The PDF reader spec depends on this one for original PDF content and downloads.
