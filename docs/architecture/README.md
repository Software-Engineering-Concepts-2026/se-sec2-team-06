# สถาปัตยกรรมโปรเจกต์ (Project Architecture)

โฟลเดอร์นี้เก็บแผนภาพสถาปัตยกรรมและบันทึกการตัดสินใจ (Architecture Decision Records) ของ **ระบบแจ้งเตือนกำหนดส่งงาน** — เว็บแอปพลิเคชันสำหรับนักศึกษา ที่ช่วยกำหนดวันเวลาส่งงาน แสดงรายการกำหนดส่งของแต่ละวิชา ช่วยวางแผนล่วงหน้า และลดโอกาสลืมส่งงาน ผ่านการแจ้งเตือนอัตโนมัติ

## ภาพรวมสถาปัตยกรรม

ระบบออกแบบเป็นเว็บแอปพลิเคชันแบบ client-server มาตรฐาน:

- **React SPA** (deploy บน Vercel) จัดการ UI ทั้งหมดที่ผู้ใช้สัมผัส: หน้าเพิ่ม/แก้ไขงาน, หน้าดูรายการกำหนดส่ง, และหน้าตั้งค่าการแจ้งเตือน
- **Node.js/Express REST API** (deploy บน Render หรือ Railway) จัดการ business logic, authentication, การบันทึก/สืบค้นข้อมูลงาน, และสั่งงาน background job
- **PostgreSQL** เก็บข้อมูลที่มีโครงสร้างชัดเจน: users, tasks (กำหนดส่งงาน), และ notification settings
- **Notification Scheduler** (background job ภายใน backend) ตรวจสอบงานที่ใกล้ถึงกำหนดตามรอบเวลาที่ตั้งไว้ แล้วสั่งส่งการแจ้งเตือน
- **ระบบปฏิทินภายนอก** (เช่น Google Calendar) ถูกเรียกเพื่อซิงค์กำหนดส่งงานเข้ากับตารางเรียน/ชีวิตประจำวันของผู้ใช้
- **ระบบแจ้งเตือนภายนอก** (อีเมล หรือ LINE Notify) ถูกเรียกเพื่อส่งข้อความเตือนเมื่องานใกล้ถึงกำหนด

สำหรับเหตุผลเต็มของการเลือก stack นี้ ดูที่ [ADR-001: การเลือก Core Technology Stack](./adr/0001-tech-stack-selection.md)

## C4 Model: System Context (Level 1)

แผนภาพ System Context แสดงระบบเป็นกล่องเดียวและความสัมพันธ์กับบุคคลและระบบภายนอกที่ระบบพึ่งพา เป็นมุมมองระดับสูงสุดของสถาปัตยกรรม เหมาะสำหรับผู้ฟังทุกประเภท รวมถึงผู้ที่ไม่ใช่นักเทคนิค

![System Context Diagram](./diagrams/c4-level-1-context.png)

**ข้อสรุปสำคัญ:**

- **นักศึกษา** เป็น actor มนุษย์เพียงคนเดียวที่ติดต่อโดยตรงกับระบบ
- ระบบพึ่งพาระบบภายนอก 2 ระบบ ได้แก่ **ระบบปฏิทิน** (สำหรับซิงค์กำหนดส่งเข้าตารางเวลาของผู้ใช้) และ **ระบบแจ้งเตือน** (สำหรับส่งข้อความผ่านอีเมลหรือ LINE) — ทั้งสองระบบนี้เป็นบริการภายนอกที่ทีมไม่ได้พัฒนาเอง
- ขอบเขตของระบบเน้นเฉพาะการจัดการ "กำหนดส่งงาน" เท่านั้น ไม่รวมฟีเจอร์อื่น เช่น เนื้อหาวิชาเรียนหรือเกรด
- การเชื่อมต่อกับระบบภายนอกทั้งหมดเริ่มจากระบบของเรา — ไม่มีระบบภายนอกใด push ข้อมูลเข้ามาในแพลตฟอร์มโดยตรง

## C4 Model: Container (Level 2)

แผนภาพ Container ซูมเข้าไปใน boundary ของระบบและแสดงหน่วยที่ deploy ได้แบบหลัก (containers) พร้อมวิธีการสื่อสารระหว่างกัน เหมาะสำหรับ developer และ architect ที่ต้องการเข้าใจ runtime topology

![Container Diagram](./diagrams/c4-level-2-container.png)

**ข้อสรุปสำคัญ:**

- System boundary (กล่องสีเทา) ประกอบด้วย **4 containers**: เว็บแอป/แอปมือถือ, API Application, ฐานข้อมูล, และตัวจัดคิวแจ้งเตือน
- **นักศึกษา** ติดต่อโดยตรงเฉพาะกับเว็บแอป/แอปมือถือเท่านั้น — ไม่ได้เรียก API หรือฐานข้อมูลโดยตรง
- API Application เป็นจุด orchestrate เดียว: รับคำขอจากหน้าเว็บ, บันทึก/สืบค้นฐานข้อมูล, และสั่งให้ตัวจัดคิวแจ้งเตือนทำงาน
- ระบบภายนอก (ปฏิทิน, อีเมล/LINE) ถูกเรียกจากฐานข้อมูลและตัวจัดคิวแจ้งเตือนตามลำดับ ตามธรรมเนียม C4 มาตรฐาน

## บันทึกการตัดสินใจทางสถาปัตยกรรม (Architecture Decision Records — ADRs)

ADR เป็นเอกสารสั้นที่ไม่เปลี่ยนแปลง ใช้บันทึก "เหตุผล" ที่ตัดสินใจเลือกทางเทคนิคที่สำคัญ แต่ละ ADR มีเลขกำกับเรียงตามลำดับและเก็บใน [`./adr/`](./adr/)

| ADR | ชื่อเรื่อง | สถานะ |
|---|---|---|
| [ADR-001](./adr/0001-tech-stack-selection.md) | การเลือก Core Technology Stack ของระบบแจ้งเตือนกำหนดส่งงาน | Accepted |

### รูปแบบ ADR ที่ใช้ในโปรเจกต์นี้

- ฟิลด์ **สถานะ** ติดตาม lifecycle: `Proposed` → `Accepted` → `Deprecated` / `Superseded`
- **บริบท** อธิบายแรงกดดันในขณะตัดสินใจ (ทักษะทีม, timeline, ข้อจำกัด)
- **การตัดสินใจ** ระบุสิ่งที่เลือกและเหตุผลอย่างชัดเจน
- **ผลกระทบ** ระบุทั้งผลบวกและลบ — เราหลีกเลี่ยง ADR ที่มองแค่ด้านเดียว
- **ทางเลือกอื่นที่พิจารณา** บันทึกตัวเลือกที่ปฏิเสธ เพื่อให้ maintainer ในอนาคตเข้าใจ trade space
- เมื่อ ADR ถูกทำเครื่องหมาย `Accepted` แล้ว จะ **ไม่ถูกแก้ไข** — หากการตัดสินใจเปลี่ยน ต้องเขียน ADR ใหม่ที่ supersede ตัวเดิม
